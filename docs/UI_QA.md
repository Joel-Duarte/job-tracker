# UI quality assurance

The `UI QA` GitHub Actions workflow runs Playwright against the Vue app with `VITE_DEMO_MODE=true`. It needs no database, backend, API keys, or Docker. Run it locally from `frontend/` with `npm ci`, `npx playwright install chromium`, and `npm run test:e2e`. CI installs Chromium's system dependencies as well.

The suite runs on desktop Chromium and a mobile Chromium viewport. `tests/e2e/views.spec.js` opens every top-level route and checks for uncaught browser errors and Vue warnings. It also exercises analytics, settings, queue, task, assessment, staging, chat, diagnostics, profile redirect, and theme controls. `tests/e2e/demo.spec.js` covers application search and archive, company creation and drawer, mobile navigation, company-form accessibility in both themes, and a desktop visual baseline. Demo data is isolated in each browser context.

This is the baseline for the full feature suite, not exhaustive coverage of every workflow. Expand it by domain as features are touched: application status transitions and detail actions; assessment decision and queue retry/cancel flows; staging resolution; candidate CV editing; company research and merge; cover-letter and Q&A previews; mock interview turns; provider and email settings; and diagnostics trace inspection. For each flow, test a successful action and at least one relevant failure or empty state with seeded or mocked demo data. Keep the route smoke tests even when more specific tests are added.

When a PR adds or changes a UI feature, extend the matching Playwright test with an observable user outcome. The workflow requires a change under `frontend/tests/e2e/` whenever `frontend/src/` Vue, JavaScript, TypeScript, or style files change. This file check cannot judge test quality, so review the assertions. Cover the relevant empty, success, and failure states when they exist, keyboard/accessibility behavior for new controls, and both viewports when layout differs. Add a demo API handler or fixture if the feature needs one. Keep screenshot baselines small and deterministic; review baseline changes as UI changes, not as a way to silence a failure.

On failure, download the `playwright-report` artifact from the Actions run. It includes HTML results, screenshots, and Playwright traces. Use `npx playwright show-trace <trace.zip>` to inspect the browser state and network activity. A maintainer can run **Actions → Jules UI QA review or fix → Run workflow** and leave the PR number blank to ask Jules to reproduce and fix failures on the default branch; a verified fix may become a PR, while passing or unreproducible tests should produce no PR. Enter an open same-repository UI PR number for a review-only session on that PR's branch. The Jules session URL appears in the job summary. Fork PRs are not supported by the PR review path. Browser QA verifies client behavior in demo mode; backend API and database integration remain covered by their own tests.

To make this a merge gate, add `Browser smoke tests` as a required status check in a ruleset for `master`. GitHub does not block merges merely because a workflow exists. Grant bypass only to designated maintainers, and explain a bypass in the PR with a follow-up issue for a failing or flaky test. Jules can review a failing trace and propose a fix, but its judgment is advisory; the required browser check remains the merge signal.
